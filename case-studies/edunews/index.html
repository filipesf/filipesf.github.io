EduNews (edunews.ie) · Solo founder / Design Engineer

Five days to live: a news site where every editorial step ships as a slash command

A Portuguese-language news portal for the Brazilian community in Ireland. Built solo, from stack choice to editorial workflow, with the publishing process committed as code instead of saved as a chat history.

At a glance

Problem
An independent publisher needed a deployable news site with a friendly CMS, search, SEO, and an editorial workflow they could actually use. No engineering team to maintain it. No hosting budget to absorb.
Role
Solo build. Code, design system, CMS, deploy pipeline, AI editorial commands, and the first production editorial cycle.

Astro 5 · TypeScript · Zod · Sveltia CMS · Pagefind · GitHub Pages
Timeframe

Live at edunews.ie in five days. A reusable design system, a Git-based CMS the editor drives directly, and an editorial workflow where every step is a versioned slash command.

Context

Independent journalism without infrastructure budget needs a stack that’s free to run, cheap to maintain, and friendly enough that the editor (who is not the engineer) can actually use it. The reader is the Brazilian community in Ireland. The editor is the journalist who runs the site. The writer (for some of the workflow) is a researcher agent calibrated to prioritise Irish-media sources and filter for the Brazilian-in-Ireland angle.

The constraints shaped almost every decision. Static site, on GitHub Pages, free at this scale. Git-based CMS, no separate billing, no parallel admin. Pagefind for search, no server. JSON-LD as NewsArticle so the site is discoverable as news. And an editorial workflow the editor can use without learning the codebase.

What got built in five days

The first three days were code and design system. The last two were AI editorial workflow and the first real publishing cycle.

Day one was scaffolding. An Astro 5 project under 04-website/, six sample articles seeded to cover every category, the deploy workflow, the editorial layout, and an initial design system foundation. The base path got added and then reverted once the custom domain was bound. A small partial roll-forward preserved in the history.

Day two was the Figma design and the design system extraction. CSS-custom-property tokens (--font-sans, --ease-out-expo, durations, layout constants), the sidebar with a configurable category filter, a 404 page with entrance animations, and the reorganisation of the article header. Then the consolidation pass: fifteen reusable Astro components extracted out of the boilerplate.

Day three was Sveltia CMS, Pagefind search, and the SEO layer. Seven YAML singletons for site config, social, navigation, author bio, footer, homepage carousel, and the optional sidebar ad. Each one is mirrored by a Zod schema in content.config.ts and a typed getter in lib/settings.ts. Pagefind got dropped in with the default UI first, then rewritten with the JS API so results render as ArticleCard-shaped cards. SEO landed as four concerns layered together: sitemap, robots.txt (excluding /admin and /busca), astro-seo for the meta tags, and NewsArticle JSON-LD on article pages.

Days four and five were AI editorial. .claude/commands/ with /research, /draft, /review, /publish, /new-article, /script, plus site-management commands. A researcher agent with Irish-media priority and Brazilian-in-Ireland editorial filtering. A human-voice skill rewritten against the editor’s tone profile. An auto-save policy that commits and pushes after any file-touching command. And then the first end-to-end editorial cycle on a real topic, a Brazilian-events guide for Dublin in 2026, plus a batch of YouTube Shorts articles. Three short and one long-form video scripts produced from the same researched topic.

The CMS contract

Sveltia is configured to write to a data/ directory of YAML files. Each one is a “singleton”. Site config, social links, navigation, author bio, footer, homepage, ad banner. The Zod schemas in 04-website/src/content.config.ts define what each file may contain. The typed getters in lib/settings.ts are the only thing components import. The pattern is strict.

  1. YAML: what the editor writes through the admin UI.
  2. Zod schema: what the code expects to read.
  3. Typed getter: the function components actually call.

Adding a new editable surface is a three-step change. Skipping any step means the contract is incomplete and something downstream will lie. The discipline took an hour to set up and saves an hour every time something new gets added.

The article permalinks went to the root of the site (edunews.ie/{slug}) rather than under an /artigos/ prefix. A small SEO call that makes the URL space feel like a newspaper, not a blog.

Editorial workflow as code

The Claude Code project is the second design system in the codebase. Where the first one is reusable UI components, this one is reusable editorial steps.

  • /research runs the researcher agent against a topic, prioritising Irish-media sources, with a Brazilian-in-Ireland editorial filter. Writes to 02-research/.
  • /draft takes a researched topic and produces a draft in 01-drafts/.
  • /review applies the human-voice skill (calibrated to the editor’s tone) to a draft, writes the revised version back to the same location.
  • /publish converts a reviewed draft into an article in src/content/articles/, ready for SEO meta and a cover image.
  • /script takes a researched topic and spins it into short-form and long-form video scripts in 05-scripts/.

Each command writes to a known location. Auto-save commits and pushes after every file-touching command, so the working state of the workspace is always recoverable from git pull. The first production cycle produced a published article with cover image and four video scripts from one research session.

The reason this matters is leverage. The same researcher agent, calibrated once, runs every research pass. The same human-voice skill, calibrated against the editor’s actual writing, applies every review. The marginal cost of producing the next article (once the workflow is in place) is a single command per editorial step, not a fresh prompt-engineering session every time.

What I’d want anyone reading this to know

The CMS is the seam, not the surface. Sveltia’s admin UI is incidental. The contract is the three-step parity between YAML, Zod schema, and typed getter. Any change to the editor’s mental model of “what they can edit” has to ripple through all three. That discipline is what stops the site from drifting into “the admin claims it can change X, but the component still reads the old value.”

Editorial workflow as code is the difference between AI as tool and AI as system. A /draft command that writes to a known folder, auto-commits, and uses a researcher agent with a specific source policy is repeatable, auditable, and improvable. A chat prompt that does the same thing is ephemeral. The same logic applies anywhere AI is going to be in the workflow more than once.

Five days is enough if the constraints are honest. The site shipped in five days because everything was static, free, and Git-based. There is no version of this build that ships in five days with a hosted CMS, server-side rendering, and a custom auth layer. And there is no need for any of those things for this product. Match the stack to the constraints and the velocity comes for free.

Decisions

Where the work actually got decided.

  1. Sveltia (Git-based CMS) over a hosted CMS

    Chose
    Use Sveltia with GitHub as the backend, configuring seven singleton YAML files for navigation, footer, ad banner, author bio, homepage carousel, and so on.
    Over
    A hosted CMS (Contentful, Sanity, Decap) with its own infrastructure to maintain and pay for.
    Why
    Git-based CMS keeps the entire site versioned in one place. Code, content, and editorial config all live in the same repo, all reviewable via diff. The editor (the journalist who runs the site, not me) writes through a friendly admin UI; the underlying change is just a commit. No separate CMS to keep running, no separate billing, no parallel access control to administer. The three-step parity pattern (YAML → Zod schema → typed getter) keeps the contract honest.

  2. Custom Pagefind JS API over the bundled UI

    Chose
    Use the Pagefind JS API directly to render search results as `ArticleCard`-shaped components, matching the rest of the site.
    Over
    Drop the default Pagefind UI in and accept its chrome.
    Why
    The first pass used Pagefind's bundled UI and the result was obvious. The search page looked like a different site. The rewrite was a few hours of work and yielded a search that reads like the rest of the editorial system. The site is the brand; a search surface that visibly imports a different design system is a hole in that argument.

  3. Editorial workflow as Claude Code commands, not prompts

    Chose
    Build `.claude/commands/` with typed slash commands (`/research`, `/draft`, `/review`, `/publish`, `/script`), each writing to a known workspace folder, plus an auto-save policy that commits and pushes after every file-touching command.
    Over
    Use Claude as a generic assistant, copy-paste between chat and editor.
    Why
    A prompt is ephemeral, a command is repeatable. Each editorial step has a known destination (`01-drafts/`, `02-research/`, `05-scripts/`), an Irish-media research filter baked into the researcher agent, and a human-voice review skill calibrated to the editor's tone profile. Auto-save eliminates the "did I save my work" tax. The result is editorial throughput that survives a fresh terminal.
