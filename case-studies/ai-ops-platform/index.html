Building the ops layer that turns multi-agent chaos into something you can leave running

A private monorepo, built solo over two focused weeks, around one rule: if the system cannot recover from what is in the repo, it is not a system.

At a glance

Problem
Running several AI agents in parallel without an ops layer means no telemetry, no idempotency, no audit trail, and no way to reclaim tasks when an agent goes offline. You end up with a demo that cannot survive a Tuesday.
Role
Sole author. Designed and shipped the API, workers, web UI, Discord bot, VM jobs, and the runbook layer that ties them together.
Stack
TypeScript · Fastify · React 19 · shadcn/ui · PostgreSQL · Redis · Discord.js · OpenCode
Timeframe
Mar 2026 (two-week build), ongoing
Impact
A multi-agent operations stack that survives offline agents, observes its own behaviour, and can be recovered from the repo at 2am.

Context

Running a handful of AI agents at the same time, one for research, one for archival work, one for marketing content, is a different problem from prompting a single agent and reading the response. There’s an assignment loop. There’s a lease-expiry policy when an agent drops. There’s a notification fan-out. There’s the question of who has permission to do what inside the Discord channel where humans and agents share a workspace. And there’s the question of what happens at 2am when something dies.

This codebase exists because none of that comes for free. The monorepo groups four services that, together, make a multi-agent setup observable and auditable: a control API, a web UI to drive it, background workers, and a Discord bot. The agent personas themselves live in a submodule. The VM layer hosts the runtimes. The runbook layer documents the seams.

Architecture

Four services share one repository, plus a submodule for agent workspaces and a VM layer for the runtime host.

The control API is Fastify 5 with PostgreSQL and Redis. Domains laid out as TypeScript modules under src/{domain,routes,services,middleware}. Activities, agents, assignments, comments, notifications, subscriptions, tasks, telemetry.

The web UI is React 19 plus Vite, composed with shadcn/ui. TanStack DataTable for the task views, Radix primitives for the surfaces that need to be accessible, cmdk for the command palette.

The workers are Redis-backed background jobs. An offline detector, an assigner, a notification dispatcher, a daily standup writer, and two bridges connecting the control plane to the agent runtime layer.

The Discord bot uses Discord.js with per-agent slash commands (one command per persona) and operational verbs (assign, audit, create, decision, permissions, report, setup, standup). Domain-based channels with localised topics. A dedicated role for the bot. A managed-role colour API fix that took a couple of attempts to get right.

The agent personas live in a single git submodule (workspaces/). That’s the result of three rounds of structural refactor. The runtime VM (OrbStack) hosts what needs to run continuously: agent runtimes, cron jobs, the OAuth-sync job that keeps a residual third-party token alive for what still needs it.

The UI build, in one day

The web UI got rebuilt in a single day across roughly fifteen commits, by design. A focused pass to get from “boilerplate with shadcn/ui” to “production-ready ops surface” before any of the more interesting features started layering on top.

The order mattered. shadcn/ui composition first. Semantic colour tokens second. Accessibility pass third (focus rings, keyboard nav, contrast). Performance plumbing fourth (shared timer, visibility-aware polling, chunk splitting, memoisation). Design-system primitive extraction fifth. Then motion. Then a brand palette. Then the deliberate “delight” layer: a toast system, a keyboard shortcut for task creation, confetti on completion, a first-visit orientation flow, contextual empty states. The final commit was a sweep through arbitrary Tailwind values to convert them to scale utilities.

The commit log carries the intent through project-specific conventional-commit scopes. polish, a11y, motion, delight, copy, simplify, color, onboarding. The grammar is more verbose than standard Conventional Commits, and it earns its keep here. Six months from now, a reader can grep for delight( to find every commit that touched the personality layer.

The assignment worker

The assignment loop is the load-bearing piece of the control plane. Tasks arrive, the assigner offers them to an eligible agent, the agent accepts, work happens, and the result returns. The interesting failure mode is what happens when an agent goes offline mid-task.

The original behaviour expired all leases uniformly when the agent’s heartbeat stopped, which lost accepted work. The fix scopes lease expiry to offered-only assignments (work that hasn’t been claimed yet) and recovers accepted assignments so the original agent can resume them when it returns. Stating it that way makes it sound obvious. The cost of getting there was a couple of incident-driven debugging sessions.

This is the kind of invariant that matters more than it announces. Distributed task queues live or die on whether their failure mode preserves work, and most of the time the only proof that you got the policy right is the things you don’t have to explain at standup.

Telemetry

You can run a multi-agent system blind. You shouldn’t. The telemetry stack is end-to-end. A collector inside each agent runtime. An ingestion endpoint on the control API. A worker that aggregates and forwards. A summary page in the web UI that anyone can open. The first version had an SSE proxy bug that masked half the events. The fix landed in the same commit as the corresponding seed migration, so the summary surface and the underlying data shipped together.

Heartbeat cost was its own story. A small RCA when the bridge worker spiked unexpectedly. The post-mortem, fixes, and the workaround for an EACCES on the delivery queue all landed in the VM runbook, so the next incident has a paper trail.

OpenCode as the agent config layer

The .opencode/ directory is how the agent presence is declared. Agents, commands, skills, model selection, MCP wiring. The pattern is declarative agent setup tied to runbooks. Agent personas are named, coloured, and given operating procedures. Slash commands are project-specific (audit, decision, report, standup, setup, permissions, assign, create). Skills got renamed to drop a legacy ff- prefix once they were no longer specific to one project.

The OpenCode config reads the runbooks first (instructions: ["RUNBOOK.md", "README.md"]). That means the agent and the human have the same starting context. The thing being optimised is whether a new contributor, human or agent, can recover the project’s state from what’s in the repo, without asking.

What I’d want anyone reading this to know

Runbooks are not documentation. They’re the operational layer. Anything that runs continuously needs a runbook colocated with the code that runs it. The four-tier layout is overkill for a side project and exactly right for an ops stack. Each runbook is written for whoever has to fix the thing at 2am, including the agent now charged with doing so.

The decisions worth writing down are the small ones. The lease-expiry behaviour. The canonical API-key auth. The convergence onto a single submodule. The rename from one namespace to another. None of these are “feature work” in a portfolio sense. They are exactly the decisions that determine whether the system stays maintainable. The commit log carries the reasoning, the runbook captures the steady-state effect, and the next incident references both.

A delight layer earns its place when the boring layer is solid. Confetti on a completed task is a nice thing to ship, but only after the assigner stops losing work, the telemetry pipeline stops dropping events, and the runbooks are actually accurate. Order matters. If the boring layer is wrong, the delight reads as cope.

Decisions

Where the work actually got decided.

  1. A single workspaces/ submodule, not one per agent

    Chose
    After three iterations, settle on one git submodule that contains every agent persona.
    Over
    Per-agent submodules, paying the pointer-bump tax on every agent change.
    Why
    Per-agent submodules were creating a steady drumbeat of pointer-sync commits, one per agent per change. Converging to a single workspaces/ submodule means agent changes ripple through one bump instead of N. The refactor was unglamorous (multiple SHA-pointer dances) but eliminated a category of operational noise that would have compounded forever.

  2. Lease expiry scoped to offered-only, with recovery for accepted

    Chose
    In the assignment worker, expire leases only for "offered" assignments when an agent goes offline. Recover "accepted" assignments so the work isn't lost when the agent comes back.
    Over
    Treat all leases uniformly. Either expire everything (loses work) or expire nothing (jams the queue).
    Why
    The original assigner behaviour was over-broad and misbehaved exactly when it most mattered, which was when an agent dropped mid-task. The new policy preserves accepted work for the agent to resume and lets offers time out without blocking the queue. It is the kind of distributed-task-queue invariant that is only obvious in hindsight, and that you only get to discover by running the system long enough for the wrong thing to happen.

  3. Runbooks live in the repo, not in a wiki

    Chose
    A four-tier layout. One RUNBOOK.md at the root for cross-service ops, plus one per service (control API, Discord bot, VM). The agent runtime is configured to read these first.
    Over
    Wiki pages, Notion docs, or "ask in the channel."
    Why
    A solo project that does not survive its author is a hobby. Runbooks live in-repo, version with the code, and are exactly what an agent (or a future me at 2am) needs to recover from an incident. Each commit's `docs(scope):` prefix maps to the runbook it modifies. The discipline cost is real and the payoff is that the system does not degrade the moment its author isn't looking.
